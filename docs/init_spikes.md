### PGPR(3) smoke

Config: `reward: cosine`, `use_pattern: true`, `max_path_len: 3` in TRAIN_AGENT and TEST_AGENT, `topk [25,5,1]`. Run in its own `tmp_dir` (`tmp/mooc_pgpr3`) after copying the reward-independent files (`dataset.pkl`, `kg.pkl`, `*_label.pkl`, `transe_embed.pkl`). Every output path derives from `args.tmp_dir`, nothing is hardcoded.

- Train 2 epochs: 72 s, exit 0. Test: ~6.5 min, exit 0.
- Metrics: NDCG 14.67, Recall 21.70, HR 36.35, Precision 4.12, 17 invalid users. UPGPR smoke had NDCG 15.10.
- UPGPR outputs in `tmp/mooc` were not touched.

Not verified, and the data points the other way:
- `use_pattern` only affects the reward (`_has_pattern` is called from the reward functions in `kg_env.py`). Beam search in `test_agent.py` does not restrict paths to patterns. The PGPR run's candidate paths include non-pattern ones (1-hop `enroll`, and `enroll > item_school > item_school`).
- Pattern 4 in `config/UPGPR/mooc.json` is `item_school` then `item_concept`, but `kg_relation` only lets a school node move via `item_school`. From the config it looks like this pattern can never match (likely a config bug in the upstream repo). Inferred from the config, not confirmed by a run.
- Consequence: before reproducing PGPR(3), check how many candidate and final paths actually fall into patterns 1-3.

### Path length 4 and 5, and the "+1" finding

**Paper protocol (p.5):** "During the training phase, to encourage the agent's exploration, we permitted the agent to traverse a path that could extend up to +1 longer than permitted during the evaluation phase." So eval len L should be trained with `max_path_len = L + 1`. The repo's `config/UPGPR/mooc.json` uses 3 for both train and test, so **the default config does not follow the paper protocol**. Policy weights do not depend on path length, so a checkpoint trained at L+1 loads fine for eval at L (confirmed: eval len 4 and 5 ran on checkpoints trained at len 5 and 6).

`topk` must have exactly `max_path_len` entries (beam search runs `len(topk)` hops). My choice, not from the paper: len 4 `[25,5,1,1]`, len 5 `[25,5,1,1,1]`.

Timings, measured one process at a time on T4 (2 epochs):

| eval / train len | train, 2 epochs total (incl. ~10 s startup) | per epoch (est.) | test |
|---|---|---|---|
| 3 / 3 (UPGPR) | 64 s | ~27 s | ~18 users/s (~6.7 min total) |
| 3 / 3 (PGPR, cosine) | 72 s | ~31 s | ~17 users/s (~6.3 min total) |
| 3 / 4 | 88 s | ~39 s | not run |
| 4 / 5 | 95 s | ~42 s | ~3.4 users/s (~32 min total) |
| 5 / 6 | 128 s | ~59 s | ~3.3 users/s (~33 min total) |

Test cost jumps about 5x from len 3 to len 4, then stays flat. Cause not investigated. Test runs for len 4 and 5 were stopped early after the throughput was stable, so no len 4/5 metrics exist yet.

**Measurement error found and fixed:** a stray len-4 test process (my `pkill -f` matched its own shell and did not kill it) ran in the background and inflated the first len-5 numbers (135 s/epoch, 1.6 users/s). The table above uses the clean re-measurement. Lesson: check `ps` for leftover agent processes before timing anything.

### Path-property analysis (on `policy_paths_epoch_2.pkl`)

Format: `{"paths": [path, ...], "probs": [[p_step1, ...], ...]}`. A path is a list of `(relation, node_type, node_id)`; the first element is `("self_loop", "user", uid)`. About 60 candidate paths per test user (393,921 paths, 6,507 users), raw length always `max_path_len`.

| Property (2-epoch models, all beam candidates) | UPGPR len 3 | PGPR(3) |
|---|---|---|
| Valid rate (ends at an item) | 91.7% | 91.9% |
| Effective length (no self-loops), mean | 2.998 | 3.000 |
| Paths using a self-loop | 0.11% | 0.01% |
| Unique relation patterns / entropy | 5 / 0.71 bits | 5 / 0.57 bits |
| `enroll > enroll > enroll` | 81.9% | 86.8% |
| `enroll > item_concept > item_concept` | 17.8% | 13.1% |
| teacher + school patterns | 0.15% | 0.08% |
| Paths with a repeated node | 0% | 0% |
| Valid paths ending in an already-enrolled (train) item | 18.3% | 19.2% |

Caveats: these are all beam candidates, not the final explanation path chosen per recommended course (`evaluate_paths` picks per user-course pair; not replicated yet). The models are barely trained, so self-loop use and pattern mix will change. The script is the cell in the Colab notebook (`/content/path_props.py`), not yet in the repo.

### GPU vs CPU

Same config (UPGPR, eval 3 / train 4, 2 epochs): T4 = 88 s, CPU only = 97 s. The script sets `CUDA_VISIBLE_DEVICES` from `gpu` in the config, so CPU-only needs `"gpu": ""` in the config (setting the env var alone is overwritten; my first attempt was invalid for this reason). GPU utilization during agent training and test stays at 0-3%. **The agent is CPU-bound; the GPU is nearly irrelevant** (TransE on CPU not measured).

## Implications

- Revised time estimate for the paper protocol (50 agent epochs; extrapolated from 2-epoch timings, so rough, and epoch time may change as the policy trains): UPGPR len 3 ~32 min train + 7 min test, len 4 ~35 + 32, len 5 ~49 + 33, PGPR(3) ~26 + 7, TransE ~12 min per seed. About **4 h per seed, about 12 h for 3 seeds**, versus the earlier 8 h guess. One UPGPR len 3 run (with TransE) is about 50 min.
- Since the work is CPU-bound with 2 vCPUs on Colab, a machine with more cores can run several (seed, config) jobs in parallel. Not tested.
- Colab free tier limits are not guaranteed (12 h maximum session, idle timeout, no published GPU quota). Keep the Colab tab open while running.
